## 1. 场景目标与产品边界

AI-TAgent 是用户主入口。用户通过聊天描述复杂目标，系统协助明确岗位、职责、资源、计划和验收标准；数字分身在批准范围内主动采集素材、执行工作、协调其他岗位、持续交付，并将可复用知识沉淀到 AKB。领导角色查看真实任务状态、交付证据和阻塞情况。

“自我进化”指可评价、可审核、可回滚的技能和工作方法改进，不指自动扩大权限、绕过审批或任意执行生成代码。

| 产品 | 负责 | 不负责 |
|---|---|---|
| AI-TAgent（Octop） | 身份与岗位、目标、规划、执行编排、协作、审批、交付入口 | 复制 AKB 知识治理或 LiteLLM 计费内核 |
| AKB | 知识来源、证据、版本、ACL、检索、知识治理及记忆服务 | 企业任务派工和人员绩效决策 |
| LiteLLM | 模型接入、路由、虚拟密钥、预算、用量 | 自动授予智能体业务系统权限 |

内部包名 `octop`、已有 API、数据库标识和环境变量不随展示品牌更改，避免破坏兼容性。

## 3. 目标架构

```text
用户 / 岗位负责人 / 领导
        │
AI-TAgent：工作台与对话规划
        │
组织 → 岗位 → 数字分身 → 目标 → 版本化计划
        │                     │
资源与权限绑定 ← 审核 → 场景运行 / 周期触发
        │                     │
Connector / API / RSS / 搜索 / 浏览器 → 证据与素材
                              │
                    分析 → 协作 → 交付 → 验收
                              │
                   记忆候选 / 正式知识候选
                              │
                      审核 → AKB 回执

所有模型调用 → LiteLLM → 获准的模型供应商
技能改进建议 → 草稿 → 检查与评测 → 审核 → 灰度 → 回滚
```

该图为目标设计，并不声称所有现有调用已经强制经过 LiteLLM。来源内容属于待分析数据，不是新的授权指令。聊天输出可以提出计划草稿，但不能直接成为权限或自动执行授权。

## 4. 分阶段实施

### P0：品牌与基础入口

- 登录页参考 AKB 布局，保留真实认证、错误处理与移动端可用性。
- 展示名称统一为 AI-TAgent / 轻智能体系统。
- 以现有组织页面为基础组织“数字企业”入口，避免只做没有真实业务数据的概览页。
- 此阶段正在恢复实施；以本轮静态检查、构建、登录行为和视觉检查结果为准。

### P1：单个数字分身的最小可验收闭环

首个场景：**企业工作情报与周报助手**。先手动、只读、可审核，再周期化。

1. 聊天或向导采集岗位、职责、目标、成功标准、时间、来源、交付对象和禁止事项。
2. 输出结构化草稿，映射已有 worker → goal → plan；草稿应明确未知项，不能虚构已连接的资源。
3. 用户选择已授权知识库、连接器、模型配置；审批快照绑定计划版本和能力版本。
4. 通过现有场景流程发起只读运行，形成来源可追溯的报告和交付物。
5. 用户按目标的成功标准验收；失败或资料不足明确标记，不能仅凭模型自述判定成功。
6. 对成功运行生成记忆候选，复用现有经理审核和 AKB 写入路径。
7. 验收后再配置周期运行，锁定审批版本和权限。变更来源、范围、交付对象或权限必须重新检查。

**首批改造位置**：Organizations 页面及其 API 模块、digital_workers 领域服务、现有场景运行入口。优先新增规划草稿合约与聚合服务，保持 HTTP 路由薄层；不把规划业务规则塞进页面或路由，不让模型直接写数据库。

**P1 验收条件**：

| 验收项 | 预期 |
|---|---|
| 未任命 Agent 或跨组织资源 | 创建/运行被拒绝，不泄露他组织数据 |
| 目标缺少成功标准、计划步骤缺少预期输出 | 不允许进入可执行状态 |
| 草稿、确认、批准状态 | 状态可见，生成草稿不触发执行、发布等业务副作用；模型请求的费用和数据发送另行披露 |
| 审批后资源撤权或能力版本变化 | 执行前失败关闭，提示重新审核 |
| 重复点击或重复审批 | 不重复派发同一运行 |
| 上游超时、凭据过期或来源为空 | 清晰失败/部分结果状态，不伪造完整交付 |
| 报告 | 包含来源、采集时间、交付物及与验收标准的对应关系 |
| 记忆候选 | 未批准不写 AKB；批准后保留审核人、来源 run 和幂等回执 |
| 周期触发 | 时区明确、禁用有效、无重叠失控；暂停和权限失效停止后续运行 |
| 测试 | 单元、API 集成、前端类型/构建及相关端到端验证均记录结果，未测项不标通过 |

### P2：统一主动采集

新增 SourceProfile 与采集结果契约：来源类型、批准的范围、查询、频率、游标、内容 hash、证据 URL、采集时间、版本、保留策略。优先 Connector/API/RSS，搜索发现、浏览器补足；实现增量去重、限速、体积限制、重定向检查、失败重试和来源失效可见性。区分“重试只读采集”与“重试有副作用交付”。

### P3：持久多岗位协作与领导视图

增加持久任务节点、依赖、负责人、验收人、交付物、阻塞原因、预算和执行租约。复用 Agent 派工能力，但不能依赖内存团队锁实现崩溃恢复。领导视图聚合真实事件和任务状态，并受组织及资源 ACL 限制；领导角色不自动拥有所有原始敏感材料。

### P4：正式知识与受控技能进化

分离会话记忆、岗位经验候选、正式企业知识和技能版本。正式知识进入独立候选审核、AKB ingestion 与回执流程。技能改进走建议、草稿、静态检查、隔离测试、评测、审核、灰度和回滚，不允许生成内容直接覆盖生产技能或扩大工具权限。

## 5. 安全、费用与审计约束

- 身份由服务端从认证用户、组织、岗位和 Agent 绑定推导，不信任模型自报身份。
- AKB ACL 始终由 AKB 执行；AI-TAgent 只能缩小范围。模型网关 key 不得作为知识库权限。规划知识入口不能以共享服务 key 替代当前用户和 Agent 权限交集。
- 密钥由后端凭据存储管理，不写进提示词、源码或前端。运行 trace 可绑定 organization/worker/run，但不得通过可伪造字段授予权限。
- 联网来源须授权；阻断元数据服务、未批准地址和重定向目标。只读浏览也须遵守账号及来源访问边界。
- 对外消息、工单、正式发布和生产变更分别设审批策略。批准读取不代表批准发送或修改。
- 配置每次运行与周期预算、并发限制和最大持续时间；达到上限停止并报告，不无限重试。取消模型请求不保证供应商不计费。
- 审计默认保存必要元数据，原始提示词/响应留存需明确授权、脱敏和保留期限。
- 技能引入不自动安装未知软件，不因“自我进化”绕过权限或安全检查。

## 6. 历史风险与恢复后验证边界

原工作区准备期间曾记录 AKB 前端类型/构建及后端跳过测试打包通过，Octop 前端类型检查通过。**这些是历史记录，不是恢复工作区的测试结果，也不是完整功能验收。**

历史调查中，LiteLLM 前端类型检查仍有基线错误；不能把依赖安装成功描述为产品验收通过。其调查基线的 `deploy/docker-compose.prod.yml` 存在默认管理员、主密钥及数据库凭据，并默认映射所有接口；`deploy/proxy_config.yaml` 开启请求内容留存；`deploy/prepare.sh` 将管理密钥用于监控 Bearer token 且文件权限为 `644`。恢复后联调前须重新检查这些文件，使用隔离配置、无真实密钥、仅 loopback 监听，并明确审计策略；不得直接启动不安全的生产默认配置。

数据库、Docker、真实模型和三项目端到端联调没有由本文证明完成。阶段完成报告须分别列明已实现、已验证、失败及未运行项。Octop 仓库规范要求发布前 `make all` 与 dashboard 构建，并保留相关跨平台与权限回归证据；若检查被网络、安全或环境限制阻止，说明阻塞而非标记通过或绕过限制。
