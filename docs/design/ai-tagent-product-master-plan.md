## 1. 产品定位与首个业务目标

AI-TAgent 是企业人员与数字岗位共同工作的主入口。与只提供聊天的助手不同，产品围绕“职责、目标、计划、资源、执行、交付、验收、复用”组织工作。数字分身是用户授权下的岗位执行代理，不是获得本人全部权限的身份替代物。

首个试点场景选为**企业工作情报与周报数字分身**：用户说明职责与关注目标，指定内部知识和外部资料来源，系统形成可审核计划；运行后产出有来源证据的报告，负责人验收，获准的经验和正式材料分别进入记忆与知识流程。

选择这一场景的原因：以只读采集和文档交付为主，能够复用现有目标、计划、场景与记忆审核；能够检验采集、规划、执行、预算和沉淀的主链路，同时避免一开始引入生产变更和对外发布的高风险副作用。

### 产品原则

1. 先可靠完成一个岗位的一项工作，再扩展多岗位自治；不以同时创建大量 Agent 代替业务完成度。
2. 聊天负责澄清和提出草案，服务端负责结构、权限、状态和可审计事实。
3. “计划已准备”“运行结束”“交付合格”“知识发布成功”是不同结论。
4. 不新造已有的组织、岗位、Agent、计划、场景或知识系统；以补齐契约和体验为主。
5. 技能进化必须版本化、评测、审核、灰度和回滚，不允许模型自行扩大权限。
6. 真实验收证据优先于演示效果。没有运行的链路明确显示未验证。

## 2. 三个产品的职责与集成边界

| 产品 | 核心职责 | 对外契约 | 不应重复实现 |
|---|---|---|---|
| AI-TAgent（Octop） | 用户主入口、组织岗位、数字员工、目标规划、审批、任务协作、交付验收 | 业务 API、运行事件、知识候选与调用身份 | 向量检索内核、模型供应商计费内核 |
| AKB | 知识来源与版本、证据、访问控制、检索、知识治理、记忆服务 | 授权检索、记忆捕获、文档入库与异步回执 | 企业任务排程与岗位派工 |
| LiteLLM | 模型协议与路由、虚拟 key、模型权限、预算、用量与成本 | OpenAI-compatible 调用、预算/用量管理接口 | 业务资源授权、知识 ACL、交付验收 |

AI-TAgent 的普通使用者不需要进入另外两个产品处理日常任务。知识管理员和网关管理员保留各产品的专业后台，不把所有管理功能简单复制到 AI-TAgent。

内部 `octop` 包名、CLI、协议头、存储键和 API 保持兼容，展示品牌使用 AI-TAgent／轻智能体系统。跨项目身份绑定不要求使用同一个 IdP；业务身份映射必须显式维护，不通过用户名同名推断。

## 4. 用户角色与主界面规划

| 角色 | 核心任务 | 权限边界 |
|---|---|---|
| 员工／数字分身拥有者 | 描述目标、查看自己交付、反馈改进 | 不因拥有数字分身而获得组织管理权限 |
| 岗位负责人／经理 | 任命 Agent、审核计划、配置资源、验收交付 | 限所属组织和岗位授权范围 |
| 领导／业务负责人 | 查看目标进展、成本、阻塞与异常 | 汇总权限不自动包含原始敏感材料读取权 |
| 知识管理员 | 知识候选审核、发布、版本与质量治理 | 由 AKB 权限决定可见范围 |
| 平台／网关管理员 | 接入、模型策略、额度和安全治理 | 不默认读取员工全部原始对话 |
| 审计员 | 查阅授权的变更、执行、发布证据 | 审计范围与内容解密权限分开 |

建议保持少量一级入口：**工作台、数字员工、任务交付、知识与集成、治理设置**。这是目标导航，不要求本轮立即迁移现有路由；先在现有 Organizations 页面形成清晰闭环，再经路由兼容测试调整导航。

工作台展示待我确认、运行中、阻塞、待验收、近期成果与预算。领导视图从任务及运行事件聚合，不以模型总结作为状态数据库。状态应同时展示“执行状态”和“验收状态”。

## 5. 核心业务闭环与数据契约

```text
岗位任命 → 数字员工 → 目标与成功标准
  → 需求澄清/规划草稿 → 就绪检查 → 人工确认
  → 版本化场景/资源审批 → 执行前重校验 → 运行
  → 交付物/证据 → 验收 → 记忆候选或正式知识候选
  → 审核 → AKB 回执 → 后续检索复用与评估
```

### 5.1 已有对象继续复用

沿用 organization、position、agent、worker、goal、plan、scene、scene version、run 和 memory candidate。保留现有版本冲突、组织权限和审计机制。计划当前状态为 draft/ready/cancelled，不在未设计迁移时随意加入新的状态值。

### 5.2 按阶段新增或扩充的契约（均为设计）

| 契约 | 必要字段与作用 | 归属 |
|---|---|---|
| PlanningDraft | 需求、约束、未知项、资源引用、步骤、预期交付、草稿版本、生成方式 | AI-TAgent；不得包含可直接执行的授权 |
| ReadinessReport | 检查项 code、结果、原因、适用对象版本、检查时间；明确未验证项 | AI-TAgent；只读检查不是审批令牌 |
| SourceProfile | 来源类型、批准地址/资源 ID、查询规则、凭据引用、频率、游标、保留策略 | AI-TAgent；优先复用连接器对象 |
| MaterialEvidence | source ID、采集时间、原始 URL、内容 hash、版本、片段、访问范围 | AI-TAgent 暂存，正式发布交 AKB |
| Deliverable | run ID、目标版本、正文/文件引用、证据列表、验收标准映射、质量警告 | AI-TAgent |
| Acceptance | 验收人、通过/退回、理由、对应交付物版本、时间 | AI-TAgent；不修改历史交付 |
| DurableWorkItem | 父任务、依赖、责任岗位、租约、重试策略、幂等键、终态 | AI-TAgent，后续持久协作阶段 |
| KnowledgeCandidate | 来源 run、交付版本、目标 KB、分类、审核、入库 run 与结果 | AI-TAgent 发起，AKB 管理正式内容 |
| SkillRevision | 能力声明、权限差异、代码/提示词版本、测试结果、审批、灰度和回滚 | AI-TAgent，受控进化阶段 |

落库之前必须逐字段确认哪些已有表可复用。数据库变更遵循仓库 SQLite/PostgreSQL 双迁移规则，迁移和升级回滚先于发布；本规划不预先承诺具体迁移号。

### 5.3 身份、费用与审计链

每次运行服务端关联组织、用户、岗位、worker、Agent、plan version、run 和 trace。模型生成或客户端传来的自报字段不得授予权限。凭据保存在后端，前端只处理引用和展示信息。LiteLLM 用量归因采用经服务端验证的标识，网关虚拟 key 不充当 AKB 凭据。

按运行记录模型用量与费用，不将估算费用描述为实际账单；预算拦截、模型重试和退款/冲正按实际网关能力验证。内部审计以必要元数据为默认，原始素材/提示词/响应留存需单独策略、脱敏与期限。

## 6. 分阶段交付路线与准入门禁

阶段以可验收成果推进，不以日历或代码行数宣告完成。

| 阶段 | 主要成果 | 依赖 | 出阶段验收 |
|---|---|---|---|
| P0 品牌与可信基线 | 登录、品牌、固定引导规划、依赖与测试清单 | 当前三仓库 | 认证回归、权限回归、构建；全量失败和阻塞有可复现记录，不隐瞒 |
| P1A 计划就绪与单次交付 | 只读就绪报告、与现有审批入口衔接、一次授权来源报告、人工验收 | P0、资源与场景能力 | 管理者可看缺项；越权拒绝；只读检查无副作用；真正运行必须再次校验 |
| P1B 对话规划 | 对话澄清→结构化草稿→人工确认→已有实体 | P1A、模型网关测试配置 | 缺失项明确询问；无效输出拒绝；模型不能执行工具或越过审批；保存幂等 |
| P2 主动混合采集与周期交付 | API/Connector/RSS 优先，搜索/浏览器补足，去重、证据、周期计划 | P1、来源契约、批准网络范围 | 超时/限速/空结果/来源撤权；时区明确；禁用立即阻止后续调度；无重叠失控 |
| P3 多岗位协作与领导视图 | 持久任务依赖、责任岗位、交付验收、阻塞上报、成本进展 | P2、持久执行状态 | 进程重启恢复、重复投递、租约过期、失败重试；领导看到真实且有权限的数据 |
| P4 正式知识与技能进化 | 知识候选发布回执、技能建议/测试/评测/灰度/回滚 | 稳定交付、AKB 入库契约、隔离测试 | 未批不发布；重复回调幂等；技能权限扩张重新审核；回滚恢复旧版本 |
| P5 企业试点与交付 | 安装升级、备份恢复、可观测性、容量与安全验收 | P0—P4 的已选范围 | 在真实目标环境完成约定验收，保留例外清单和运维手册 |

### 6.1 下一轮具体切片：计划就绪检查

目的不是增加一个漂亮评分，而是让经理知道“这份计划缺什么、为何不能进入下一步”。优先从已保存的目标与计划读取，不要求新建数据库对象。

实施顺序：

1. 先核对当前 worker/goal/plan 与场景校验，提取可复用检查，避免前端/后端各有一套不同结论。
2. 领域服务生成结构化检查结果，HTTP 层只做鉴权、参数解析和返回。
3. 检查只覆盖代码能够核实的事实，例如员工与目标状态、计划内容、任命、已绑定资源的可见性；不通过外部探测假称模型或知识库可用。
4. 前端展示逐项缺失、警告和检查边界；不得通过“就绪”标识跳过场景审批。
5. 测试覆盖组织越权、缺少任命、空计划、非激活目标、版本变化、资源撤权和零副作用。
6. 针对最终实现同步文档。未实现的检查保持“未检查”而非默认通过。

推荐输出字段是设计建议，由实现先审视现有 API 类型后确定。不得将 readiness 缓存当授权；审批和执行仍以当时状态重新校验。

### 6.2 随后的真正聊天规划

复用现有模型配置，经 LiteLLM 测试虚拟 key 调用；首先使用结构化输出和 schema 校验，限制步骤数量、字段长度、资源引用与总预算。规划模型仅获得必要岗位上下文，无执行工具。错误、超时和不完整输出产生可编辑草案或明确失败，不静默保存为 ready。

向用户展示“由模型建议／由用户修改”的来源。确认的是具体计划版本及资源范围，不是对未来全部行为的笼统授权。保存与执行分离，模型调用成功也不表示计划已获批。

## 7. 采集、协作、知识与进化的关键设计

### 素材采集

- API/现有 Connector 优先，RSS 次之；搜索负责发现，浏览器负责必要的页面读取。
- 来源白名单、重定向目标、内网/元数据地址和体积限制由可信执行层校验；网页内容不得变成指令。
- 依据 source + content hash/版本去重；保留采集时间、失败原因与来源变化；不要把“没有新材料”当作失败。
- 只读重试与对外提交重试分开，后者必须幂等与可查询回执。

### 协作与管理

- 大目标拆成有预期交付和验收人的任务，不只是一组 Agent 对话。
- 每次派发形成持久工作项，记录依赖、租约与尝试；内存锁仅作单进程优化。
- 领导看板显示目标、完成/验收比例、阻塞、交付证据与预算。百分比必须给出分母，不能由 LLM 自由估计。
- 人员绩效和敏感人事决策不自动从聊天/私密数据推出，岗位仿真不等于对现实人员作决策。

### 知识沉淀

- 临时素材、会话记忆、岗位经验、正式知识分开处理。
- 复用现有记忆审核；正式文档走独立候选、目标 KB ACL、版本与 ingestion 回执。
- 入库请求接受、解析成功、索引完成、可检索是不同阶段；只有确认达到约定阶段才报发布完成。
- 源资料撤回或授权变化要可定位影响的交付和知识版本，不复制不可追溯文本。

### 自我进化

- 运行反馈可以形成技能改进建议，不直接覆盖正在使用的技能。
- 新技能声明需要哪些工具、联网来源和数据权限，自动比较旧版本差异。
- 先静态检查和隔离测试，再针对固定评测集评价效果和成本；批准后小范围灰度，保留回滚。
- 不因目标未完成而自行安装未知软件、暴露凭据或申请无限预算。

## 8. 验收、质量和交付标准

每个切片交付：代码、测试、用户入口、状态说明、运维/权限变化、失败路径及验证清单。报告分成已实现、已验证、已失败、未运行四类。

关键验收矩阵：

| 维度 | 必测案例 |
|---|---|
| 权限 | 普通成员/经理/跨组织、Agent 取消任命、KB 撤权、虚拟 key 失效 |
| 一致性 | 乐观版本冲突、重复点击、重复审批、重启、回调重复和乱序 |
| 规划 | 空字段、无成功标准、无效资源 ID、模型 schema 错误、超预算 |
| 执行 | 上游超时、部分结果、取消、无证据、未知终态不盲目重放 |
| 知识 | 未批准不写、重复发布、入库失败、索引未完成、内容版本变化 |
| 体验 | 中英文、移动端、加载/空态/失败态、返回与取消、不丢草稿 |
| 安全 | 提示注入、凭据不出浏览器/日志、内容留存策略、敏感来源隔离 |
| 部署 | SQLite/PostgreSQL 兼容、迁移、备份恢复、回滚、并发与资源上限 |

工程门禁遵守仓库 `make all` 和前端构建要求；受阻检查不能凭定向测试替代为全部通过。针对上一轮遥测拒绝，不重复受拒操作或更换通道规避；应先明确目标和数据、获得必要许可或以获准方式修复触发问题，再恢复对应检查。

容量与质量指标在试点中测量：单次运行耗时/费用、交付验收率、证据覆盖率、重复采集率、权限拒绝正确性、故障恢复时长。初期不编造吞吐量或“自治率”；先固定场景、数据规模、模型和测试环境，再设置目标。
