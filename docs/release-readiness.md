## 当前评估

**结论：当前工作区是待验证的发布候选，不能直接视为已批准的生产版本。** 本分支包含虚拟员工档案、阶段目标、工作计划、审批执行和能力改进提案等功能；相关代码和规格文档仍有未提交改动。测试通过只说明相应代码门禁通过，不替代代码评审、版本化、发布制品验证或目标环境演练。

本结论只描述当前仓库检查状态。实际发布决策应以本次发布填写的验证结果、未关闭问题、部署环境和业务风险为准。

### 发布前必须完成

- 将代码、迁移、规格和变更日志一并评审并提交；确定发布版本号及源代码提交 SHA。
- 运行仓库门禁 `make all`（全栈 lint、类型检查和后端测试）；单独执行前端生产构建 `npm run build` 或 `make build-frontend`。已知 lint warnings 应评估并记录，不能把 warning 当成测试通过之外的安全保证。
- 在 SQLite 与 PostgreSQL 的目标版本上，从受支持的旧 schema 和空库分别验证迁移；覆盖迁移后读取、写入、并发审批冲突和虚拟员工执行链路。
- 按下文完成目标环境备份、升级、健康检查和恢复演练；验证模型服务、连接器、凭据、反向代理/TLS 和出站网络策略。
- 评审权限边界、日志脱敏和供应链/依赖风险；记录安全审查、未解决问题、负责人和处置期限。
- 构建并安装实际发布制品（Wheel/容器/桌面制品中本次承诺支持的部分），验证版本、架构和哈希，并执行最小端到端验收。

## 变更范围与运行边界

当前候选新增的虚拟员工能力通过组织角色、岗位任命的 Agent 和现有企业场景审批/执行工作流工作。能力提案发布只更新 Octop 内部版本化能力档案，不会自动编辑 Agent 系统提示、生成知识库文档或授予技能包、知识库、Connector 权限。技能包和知识库执行引用必须在 Agent 当前授权资源范围内；审批和运行前会重新检查授权。企业运行仍是一次性审批任务，不是无人值守的周期性工作流。

运行生产验收时，至少覆盖：

1. 组织所有者/经理创建员工档案、目标和计划；普通成员无权写入。
2. 已准备计划匹配企业场景申请执行，申请人不能审批自己的申请。
3. 撤销 Agent、Connector、技能包或知识库授权后，待审批申请不能越权执行。
4. 两名经理并发审批/发布时，过期版本请求冲突且不覆盖新数据。
5. 非成员和无关用户无法读取员工、运行证据或提案；失败和拒绝状态可追踪。

## 数据库升级与回滚

Octop 会在服务启动时自动应用编号迁移。发布包含新的 SQLite 和 PostgreSQL 成对迁移时，需确认两种文件版本一致、目标 schema 具有预期表/约束/索引，并分别验证目标数据库驱动。

### 升级步骤

1. 记录当前 Octop 版本、提交 SHA、数据库类型/版本、schema 版本、部署配置和数据目录位置。
2. 暂停会写数据库或工作区的服务入口，确保备份时间点一致。
3. 执行 `octop backup`，并按部署使用的数据目录/对象存储策略额外备份 Agent 工作区、上传文件、密钥配置及其他持久化数据。验证备份文件可读取，并在隔离环境实际恢复一次。
4. 部署本次构建的不可变制品；首次启动前保留数据库副本。启动日志确认迁移成功并记录新 schema 版本。
5. 调用 `GET /api/health`，验证登录、模型连接、一个普通 Agent 对话及一个企业场景/虚拟员工最小流程。
6. 检查错误日志、审计记录、备份作业和资源使用情况；观察到稳定后再恢复全部流量。

### 回滚原则

数据库迁移不应假定可以安全降级。若新版本已写入新 schema 或新业务数据，优先停止写入并评估向前修复。确需回退时，恢复升级前一致性备份并同时回退应用制品和关联文件数据；不得只恢复数据库而保留升级后工作区/文件。

恢复前保存故障现场副本及日志，记录数据丢失时间窗口和回退负责人。恢复后验证 schema 版本、用户认证、Agent/工作区数据、关键业务记录及健康检查，并由业务负责人确认恢复点满足要求。
