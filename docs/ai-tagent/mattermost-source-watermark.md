# Mattermost 来源高水位（隔离验证）

本阶段修复 43506ab 的重复受理缺陷：v1 首次受理、v10 重复受理后只存 v1，
导致随后 v2 重复受理、v3 取消仍被允许。生产接收器仍未挂载，真实执行和外发未开放。

## 持久化与业务边界

schema 046 增加 `observed_source_version`，保存匹配当前已保留身份且经过当前权限验证的
可信来源最高版本。原 `source_version` 保留最后一次业务变更版本。
查询返回 `source_version` 为观察高水位，并增加 `state_source_version` 表示业务版本。
仅推进观察不改变 pending/cancelled、业务 revision 或更新时间，不授予执行权限。
对端需复核此响应语义；Go v2 proof 签名字节未改变。

受理和取消在来源身份匹配后，先独立提交高水位与 `mattermost.source_observed` 审计，
再检查来源业务状态并执行原业务事务。故来源状态拒绝、CAS 冲突或后续业务事务回滚，
不会抹去已成功持久化的观察。403/409 不再意味着完全没有写入。
业务事务会重新读取高水位；其他连接先提交更高观察时，旧操作不能覆盖它。
查询只读取已保存状态，不宣称向真实来源实时查询。初次受理将两个版本一起落库；
不存在的身份不会仅凭观察预先创建业务记录。

观察事务自身写入或审计失败时整体回滚，并阻止后续业务动作：未能落盘的观察无法保证留存。
提交确认丢失可能返回 503，但已提交水位保留；应以原 delivery key 查询核对，不换身份重投。
保障范围是当前数据库保留历史，备份回退/来源版本重置仍缺少跨系统 epoch 策略。

## 升级兼容

046 将已有业务版本复制为初始高水位，但这不能重建过去未保存的更高观察。
因此迁移会禁用所有已有 intake 的 broker；没有 intake 的 broker 不受此禁用影响。
不提供自动重新启用路径：需要可信历史核对/epoch 方案，不能简单开启 enabled 就声称安全。
SQLite 中新增字段、初始化、禁用与 schema 版本在同一显式事务内；故障回滚后可重试。
PostgreSQL 有配对 SQL 并使用已有迁移事务，但本轮未运行真实 PG。

## 验证与剩余边界

仅临时合成 SQLite、ASGI 和签名 MockTransport：

- v1 → v10 → v2 回退拒绝、取消 v3 拒绝，较新取消及重复取消只提升观察。
- 不允许的来源状态仍保存匹配的更高观察；CAS 失败不丢水位。
- 两个独立连接竞争、取消前被另一连接推进水位、重开连接后的持久化。
- 观察审计失败、业务取消审计失败、提交确认丢失及迁移失败回滚/重试。

定向测试 83 通过；恢复镜像、proof 和发布 API 回归 161 通过。
静态 lint/typecheck 单独执行；没有运行受限遥测测试或全量 make all。
没有真实 Mattermost 双服务、生产 TLS/密钥注册、真实 PG 或真实外发验收。
现有 nonce/intake 容量仍有硬上限且无安全回收流程，本轮未新增管理诊断界面。
这项修复不构成 1.0 发布批准。
