# 旧启动迁移回退链路修复（schema 049）

本阶段撤回 86181b6 中“schema 048 足以拒绝旧维护程序”的判断。实际旧 c590d088
`run_migrations` 会经 `_reconcile_pre_squash_schema_version` 把 48 降成 47，随后旧维护
程序满足版本条件、重新启用 broker，旧 0e950452 仓储再次能读取隔离 key。
仅测试旧仓储、跳过旧启动迁移不足以证明该链路安全。

## 实际修复

- 新程序在任何兼容修复前检查 schema；高于本程序认识的版本时以
  `DATABASE_SCHEMA_NEWER_THAN_BINARY` 拒绝，不能静默压低未知新 schema。
- schema 049 再次禁用存在 retired 记录或历史 retire_and_resume 审计的启用中 broker。
  记录 schema-migration 审计，不新增永久隔离记录。
- SQLite 在数据库内安装 schema 下限触发器：禁止将版本降到 49 以下、插入低版本或删除
  schema 行。真实旧迁移尝试降级时由 SQLite 拒绝，不依赖旧程序认识新的应用协议。
- 独立 broker 触发器拒绝重新启用有隔离记录或历史启用审计的 broker。即使测试中人为
  移除 schema 下限约束并重建 47，真实旧维护方法仍在写 enabled 时被此约束阻止，整个事务回滚。
- 约束安装、保护性禁用、审计和版本更新在同一 SQLite 事务；失败可回滚并重试。
  PG 提供配对函数/触发器 SQL，但未做真实 PG 验证。

这些是**被测旧 SQL 路径的防护，不是进程隔离或防混跑保证**。同 UID/数据库所有者可以
移除触发器、改库或使用其它版本路径；旧迁移还可能在降级被拒绝前执行其它兼容修复。
不能据此宣称旧进程已停止、没有任何旧写入、已读数据被收回或已发出任务被取消。

## 启用和恢复边界

`retire-and-resume` 仍无条件返回 `MAINTENANCE_PROCESS_ISOLATION_UNPROVEN`。
不提供“忽略旧进程检查”开关，不接受操作者自报的停服布尔值。
原地/在线恢复及隔离镜像激活仍关闭，不能在现有业务库上以本修复为依据执行恢复。
要解除阻断，仍需受信任监督器/存储访问边界能强制阻止旧二进制访问，且具有实际部署验收证据。

已由旧 047 隐式创建的 fence 仍保留，不自动清除，也不视为用户追认。
049 不恢复任何旧任务或授权；不修改 OS 安全/网络设置，不连接生产，不真实外发。

## 保留备份与隔离镜像能力

恢复镜像原先拒绝一切触发器。049 的正常备份包含四个保护触发器，因此现在只允许
与随包 `049_mattermost_storage_guards.sql` 完全一致的 `(type,name,table,sql)` 集合。
仅同名不够：改写、缺失、额外触发器或任何视图均在隔离写入前拒绝，trusted_schema 仍关闭。
旧 schema 归档仍不得带触发器。正常 049 备份可生成隔离镜像，但账号和 broker 仍全部禁用，
镜像仍不能用作服务启动或原地恢复。

`041f19a3f17beb1e414b5b8767524e3cc9cf8dd846e4195430f53f91bd8c5431`），
为其构建 001–047 的完整发现目录；001–046 使用未改变的迁移文件，047 使用归档原文
`047_c590d088.sql.txt`（SHA-256
`b283ebaf6637c47d5dba421939c0c442ec32889510eb078ba5946547e1ee477c`）。
旧维护和旧仓储亦使用此前保存的原始模块。

在临时合成库中，先完整复现 **旧迁移 → 48 降 47 → 旧 resume → 旧读取成功**，再迁移到
049，验证旧启动降级失败、旧维护版本拒绝、独立 broker 约束拒绝启用、审计与写入回滚。
另保留独立旧仓储子进程跨迁移的连接测试；它不是完整旧服务部署验收。
历史布局测试移除 049 约束仅为构造“尚未存在约束”的临时数据库，没有产品入口允许此操作。

待办审批入口的未提交修改已暂存，未混入本安全提交；该用户断点仍待后续完成。

## 后续修正：正常启动也必须校验完整定义

独立复核发现：049 库的两个 guard 被删除后，先前的正常 `run_migrations` 仍会返回成功；
旧迁移及旧维护程序随后仍可走不安全路径。仅在恢复镜像校验 DDL 不足以保护正常启动。

现在正常 SQLite 启动在 `_repair_legacy_schema`、迁移和任何兼容修复之前，比对随包 SQL
中四个 guard 的完整 `(type,name,table,sql)` 定义。schema≥49 缺失任何一个、同名定义修改、
同名对象类型/绑定表错误均以 `DATABASE_SCHEMA_GUARDS_INVALID` 拒绝。
低于 49 的 watermark 若残留任何 guard 也视为不一致并拒绝。
**不会自动重建 guard，也不会通过重建宣称缺损期间的历史安全。**

已配置数据库的 `OctopServer.start` 将此检查和迁移移到插件、能力探测及共享服务/运行时
构建之前；`bind_control_plane` 同样先检查。失败会关闭新打开的连接，不绑定服务。
完整 guard 的正常启动、旧 schema 正常升级和首次安装仍走既有流程。

这是对启动时损坏/不完整保护定义的检测，不是持续监控或排除同 UID 写入者。
检查后有人改库、全部 guard 与 watermark 同时被伪造为旧布局，或直接运行不认识新检查
的旧程序，不在这个检查的保障范围。无法证明历史完整性时应保持停用并调查，不能以
原地恢复、直接降级或补建触发器绕过。`resume` 和恢复激活仍关闭，PG 尚未实测。
